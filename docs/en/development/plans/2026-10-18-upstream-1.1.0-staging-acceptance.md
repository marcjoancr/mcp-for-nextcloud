# Upstream 1.1.0 staging acceptance plan

> **For agentic workers:** use `superpowers:executing-plans` for authorized
> execution, with phases and evidence recorded in order. This is an acceptance
> procedure, not a request to implement code. Writing or approving this plan does
> not authorize installation, remote exposure, sending data to hosted clients,
> recovery operations, push or production deployment.

**Goal:** close the remaining human and environment-specific acceptance gates for
upstream 1.1.0 without conflating local qualification with production readiness.

**Architecture:** test the immutable capability-based package through real
Nextcloud, proxy, browser and client boundaries. Keep one source of truth for
operational behavior in the existing guides; record observations and human
approvals separately, with no compatibility layers or temporary production code.

**Tech stack:** app ID `mcp`, PHP >=8.2, Nextcloud 32–35, native OAuth/DAV,
operator-selected supported database/cache/storage/proxy, and versioned real MCP
clients and browsers. Match PHP to the selected Nextcloud host's own requirements;
the application's PHP floor does not certify every host/PHP combination.

**Spec:** [integration plan](2026-10-17-upstream-1.1.0-capability-integration.md),
[technical closure](2026-10-17-upstream-1.1.0-integration-report.md),
[exclusion contract](../contracts/exclusion-and-folder-exposure.md),
[installation/recovery](../../installation.md), [permissions](../../guides/permissions.md),
[OAuth](../../reference/oauth.md) and [translation policy](../translations.md).
The companion [human checklist](2026-10-18-upstream-1.1.0-human-review-checklist.md)
owns per-page, language and assistive-technology approval.

## 2. Global constraints and evidence rules

- No production accounts/data, credentials, database backups or raw HTTP/browser
  traces in Git, issues or shared artifacts. Use named synthetic fixtures. Review
  HAR, URLs, screenshots and logs for codes/tokens, cookies and private identifiers
  before retaining a sanitized extract; never disable redaction for convenience.
- Keep credentials, backups and harness state in operator-controlled private
  storage outside the repository. Project-local generated verification outputs
  may use ignored `mcp/build/verification/`; committed reports carry sanitized
  evidence IDs, digests and approved retention locations, never secrets.
- Provisioning, reachability and fault injection require an approved target and
  recovery owner. Keep local servers/ports on loopback; any remote exposure must
  be explicitly authorized. Do not weaken TLS, CSP, CSRF, brute-force protection
  or native ACLs to obtain a green result.
- Execute S0–S7 in order; failures stop dependent phases. Human reviewers can read
  frozen documentation earlier, but rendered UI approval follows the deployed
  candidate. A change to reviewed content invalidates its affected approval.
  Record each global mutation's fixture reset and starting state before the next
  scenario; revoked credentials are replaced by fresh consent, never restored by
  undoing a setting. Failures leave the target isolated and MCP closed as needed.
- Do not rerun the destructive native integration runner against a standing staging
  instance. Its disposable matrix is separate evidence; follow the
  [native test guide](../../../../mcp/tests/Integration/README.md) if a changed
  candidate requires requalification. Do not use filters/version overrides as
  final qualification or run concurrent builds in the same checkout.
- Use the final owners, framework migrations and jobs. No SQL shortcuts to approve
  policy, forced migration reruns, version bumps to trigger replacement, production
  test bypasses, dual implementations or transition directories.

Every result records: scenario ID; UTC time; operator/reviewer; source and package
hash; environment ID and versions; fixture roles; steps; expected/actual outcome;
sanitized evidence reference; `PASS`, `FAIL`, `BLOCKED` or `NOT APPLICABLE`; defect
and retest references. Use `NOT RUN` before execution. An exit code or screenshot
alone is not proof of a completed state transition. A not-applicable decision needs
a reason, owner and explicit limit on the acceptance claim. Missing access, apps,
reviewers or client accounts is `BLOCKED`, not `PASS` or `NOT APPLICABLE`.
Full closure requires C1a–C1e, C2–C4, F1–F7 and all human checklist sections.
Deployment-specific subcases (such as a proxy base path not in use) may be
not applicable with evidence; entire required rows may not be waived. If a target
lacks an external group backend or federation partner, authorize a separate
representative fixture environment or retain partial evidence. Never install an
unplanned backend or use a production federation partner to satisfy the checklist.

## 3. Review focus

1. Wrong-origin, replayed or withdrawn OAuth credentials must not gain admission
   through the real proxy/client route (S3).
2. Hidden files, aliases and cross-module references must not leak through native
   mounts, ACLs or federation; positive visible controls must still work (S4).
3. Stale browser state, uncertain policy and delayed responses must not save to the
   wrong user or claim a failed/unknown operation succeeded (S4/S5).
4. A restored backup must not revive revoked credentials or lose required scopes
   when traffic reopens (S6).
5. Translated security instructions and real assistive-technology feedback must
   preserve the English contract and usable confirmation/recovery paths (S5/S7).

## 4. Phases and acceptance criteria

### S0 — Freeze the candidate and authorize the acceptance target

Owner: maintainer and staging operator. Produces the run manifest and approval
record consumed by every subsequent phase. The requesting user has accepted host
ownership and operation/recovery responsibility; reviewers/final approver and action
authorizations remain pending. The accepted lifetime is a bounded validation campaign,
not a 30-day allocation. This changes duration, not scenario coverage or acceptance
criteria; preparation of a future upstream PR does not imply S0–S7 approval.

- [x] Resolve all pinned commits, verify the archive digest and record the full
  candidate identity. Preserve the qualified archive before building anything else.
  Completed in the S0 report; the preserved copy is not an independent backup.
- [x] Select fresh installation or the exact existing origin before S1 fixture setup.
  The user accepted the proposed fresh isolated devbox target in the
  [decision record](2026-10-18-upstream-1.1.0-staging-acceptance-report.md#confirmed-decisions--short-validation-campaign).
  No installation is authorized; target hostname/access remains in the next gate.
  Any additional upgrade origin must use the original/local 1.0.8 or upstream 1.1.0
  [native matrix](../../../../mcp/tests/Integration/ci/matrix.json) pins and its own
  separately approved isolated baseline.
- [ ] Record the target hostname, Nextcloud/PHP/database/app versions, proxy, cache,
  cron mechanism, storage mounts, group backend, theme and client versions. Identify
  the intended deployment topology and every difference from it.
- [ ] Name the operator, security reviewer, language reviewers, accessibility tester
  and final maintainer. Record authorization for installation, fixture mutations,
  external-client traffic, any federation partner and the S6 restoration exercise.
- [ ] Select the real client coverage below and confirm credentials/accounts are
  available privately. Verify current client setup against its official
  documentation when executing; historical guide screenshots are not evidence of
  current availability or UI. Record versions/dates and necessary guide corrections.
- [ ] Confirm a consistent backup/restore procedure, recovery owner, maintenance
  window and intended recovery point/time objectives (RPO/RTO) before any target
  mutation. Define the measurement start/end and data-loss comparison, not just
  numeric targets; missing operator-approved objectives block S1. Identify a
  private administrative path that can perform supported recovery commands while
  public ingress stays closed, including when Nextcloud maintenance blocks HTTP.
  Missing safe administrative access blocks the recovery exercise.

Acceptance: manifest complete, exact target/candidate and recovery design approved,
with defined synthetic fixtures and no unresolved authorization or identity
ambiguity. For a fresh target, S0 identifies safeguards and owners; S1 verifies
operability on the authorized environment and S6 demonstrates recovery. Do not
provision a target merely to claim S0 readiness. This plan alone supplies none of
those external approvals.

### S1 — Establish representative staging and fixture boundaries

Owner: staging operator. Consumes S0; produces an isolated environment and baseline.

- [ ] Prepare the authorized topology with matching proxy, cache/cron, supported
  optional apps and storage behavior. Disable outbound real notifications; use a
  test mail sink for SMTP. Configure only approved hosted-client/federation traffic.
- [ ] Seed native administrator/Alice/Bob/disabled accounts, database-backed groups
  and the approved external group backend. Prepare visible/excluded files, local
  shares, groupfolders with advanced ACLs, an external mount, VEVENT/VTODO collections,
  and references in Talk/Tasks/Calendar. Use dedicated fixtures for destructive
  identity tests; do not remove the recovery administrator's access.
- [ ] For an existing origin, seed only the MCP settings and valid credentials that
  origin supports, then record their pre-upgrade behavior. Native 1.0.8 has no 1.1.0
  resource-scope rows to seed or preserve. For fresh installation, defer all MCP
  configuration/credentials to S2; absence of pre-existing credentials is expected.
  Do not install the candidate early just to manufacture an upgrade baseline.
- [ ] Record native Nextcloud access for every visible/denied fixture before MCP
  requests. Include distinct storage/file IDs and a controlled remote federation
  partner for F4 below. Record absent required coverage as blocked.
- [ ] Verify maintenance access, backup readability, cache restart procedure,
  scheduler execution and sanitized logging. Capture policy/connection baselines
  without dumping credentials or database rows into the report.

Acceptance: fixtures exercise actual configured trust boundaries, native ACL
expectations are known and the environment can be restored without touching
production. Reduced topology evidence must not be labeled full upstream closure.

### S2 — Install or replace the exact candidate

Owner: operator, witnessed by maintainer. Uses the canonical installation guide.

- [ ] Confirm the S0-selected origin and S1 baseline. The other paths already have
  disposable evidence in the closure report; do not pretend they were repeated in
  staging. Test each additional selected origin on its own isolated baseline.
- [ ] Quiesce writes/enter maintenance and take a consistent coordinated backup
  before replacing app files. Follow the installation guide, replace the complete directory, preserve original
  migration IDs, and restart PHP caches as needed. Routine maintenance must not
  toggle MCP policy merely to stop traffic and thereby revoke existing credentials.
- [ ] Verify installed version and deployed file manifest against the artifact,
  migration history, both registered jobs, assets and original preferences. Verify
  preservation of scopes/managed clients only for an origin that already has them;
  verify the expected migration defaults/import for 1.0.8. Same-version replacement
  must preserve state without forced migrations.
- [ ] After verifying the deployed files/schema, lift maintenance behind the
  approved staging ingress boundary. Confirm legitimate existing fixture connections
  survive the selected ordinary upgrade path; record preservation as not applicable
  for a fresh install. Record and investigate schema/index diagnostics instead of hiding
  warnings or treating an `occ` zero exit status as proof of completion.
- [ ] After preservation checks, configure the final S3–S5 fixture permissions,
  eligibility, personal connections, scopes and clients through supported controls.
  Record before/after state: on a fresh install the built-in native client starts
  disabled and no custom clients exist. Explicitly registered custom clients may
  be enabled; upgrades must preserve legitimate prior settings. Keep all access
  on the approved staging route with the intended boundaries intact.

Acceptance: the installed bytes and state match the candidate and expected origin;
no stale app files or accidental policy reset; jobs and assets load. An unresolved
upgrade or preservation defect blocks traffic-based acceptance.

### S3 — Exercise real clients, proxy and credential lifecycle

Owner: client tester and security reviewer. Use non-sensitive fixture content only.
All documented client families need actual-client evidence for full closure;
each Claude surface claimed in the guide is a distinct row, not inferred from
another Claude product's result.

| ID | Real-client coverage | Required positive and negative observations |
| --- | --- | --- |
| C1a–C1e | Claude web (C1a), Desktop (C1b), Cowork (C1c), Code (C1d); ChatGPT (C1e) | Record each independently. Discovery/challenge uses the external HTTPS origin; published identity login, consent, denial, callback issuer, tool discovery and a permitted read work. Removing its allowed host refuses admission even after caching. |
| C2 | Gemini CLI with built-in native client | Disabled by default; explicit enable permits PKCE and documented variable-port loopback callback; disable/re-enable does not revive old codes/tokens. |
| C3 | One operator-selected registered public client | Exact callback, including loopback port, works; different callback/port is refused. Client disable/delete or redirect removal withdraws old grants; fresh consent succeeds after legitimate reconfiguration. |
| C4 | One actual HTTP Basic MCP client | App password plus service/eligibility/personal connection and native permissions are required. MCP disconnect blocks MCP use; native Security revocation separately invalidates the app password. |

- [ ] Record each exact application/build/account feature availability and perform
  the C1a–C1e and C2–C4 journeys through the real proxy, not only a curl substitute.
  For every client include tool discovery, a permitted read, a permitted fixture-only
  write using the tool's confirmation flow, and a refused operation. Unavailable
  client access stays blocked and limits the claim until tested or documented
  support is deliberately revised and re-reviewed.
- [ ] Observe redirects, issuer/resource metadata, forwarded scheme/host, base-path
  handling if used, Authorization forwarding, streaming/reconnect and timeouts.
  Verify consent framing and CSRF protection; no mixed-content/CSP workaround.
  Check non-admin administrative API requests and missing/invalid-CSRF writes:
  server-side refusal must leave state unchanged, not merely hide a browser button.
- [ ] Use a controlled protocol fixture alongside real clients to check code reuse,
  wrong PKCE, refresh rotation/replay, stale consent and revoked access/refresh/code
  refusal. Never extract real client secrets into the shared evidence report.
- [ ] Test service shutdown, personal disconnect, loss/regrant of eligibility,
  account/group recreation and client withdrawal. Fresh authorized credentials
  must survive deferred cleanup of old generations; log job completion privately.
- [ ] Check test SMTP notifications or errors for the configured workflows through
  the sink; verify no credential/content leak or accidental external recipient.

Acceptance: every required client row works within its documented grant boundaries;
withdrawn credentials remain invalid, no proxy-origin/authentication workaround,
and notification handling is understood. Unsupported or unavailable surfaces
cannot be counted as passed because local protocol tests passed.

### S4 — Verify permissions, mounts and structured-reference privacy

Owner: security reviewer with storage/group operator. Use allowed controls beside
each denied case; test Basic and Bearer and both discovery and direct calls.

| ID | Scenario | Acceptance oracle |
| --- | --- | --- |
| F1 | Individual allow/deny, database group inheritance, external/ambiguous groups, removal/recreation | Individual override precedence is retained; untrusted or uncertain group identity never silently grants. Unknown yields temporary refusal where required, not credential erasure. |
| F2 | Independent Files, Calendar and Tasks scopes; empty selected set; mixed VEVENT/VTODO collection | Empty restricted scope admits none, unrestricted adds no filter; components remain distinct. New scopes narrow the next operation without OAuth revocation or new native rights. |
| F3 | Excluded ancestor, local share alias, groupfolder advanced ACL allow/deny, narrow external mounts | Native denial wins; hidden items are omitted/refused generically. Distinct mount IDs do not imply cross-storage tag inheritance. Test browse/read/write and share/link exposure. |
| F4 | Two controlled federated servers with local and remote tags | Local mounted-path protection applies; remote-only tags are not claimed to propagate. Verify visible/locally excluded controls; document operator acceptance of this limitation. |
| F5 | Talk attachment IDs/URLs, Task ATTACH, Calendar fields, Deck counts, preview/resources, existing folder links | Protected structured references do not escape. Stored DAV content stays intact; counts/free text are not claimed to be a general DLP filter. Notes/Contacts/Deck/Talk do not acquire invented module scopes. |
| F6 | Folder copy/move/share with exclusions, same-parent rename, checkout/locks | Forbidden exposure is refused before mutation; folder share URL is null where required. Allowed controls and lock handling remain correct; temporary checkout failure leaves its unspent link retryable. |
| F7 | Admin inspector versus MCP/personal output, log privacy and filters | Only administrators see diagnostic scope explanations; no other user's state or token hashes. Default log privacy does not expose hidden paths/content through filtering or errors. |

- [ ] Execute F1–F7 with fixture identifiers and native positive/negative controls;
  record exact affected operations rather than a single “permissions passed” claim.
- [ ] Observe cold and warm nodes/processes during changes, including exclusion
  appconfig and native group/app/user caches. Record time to convergence and
  requests already in flight. The inherited approximately three-second appconfig
  TTL plus request time is a limitation, not a new instantaneous guarantee.
- [ ] Distinguish an uncertain operation grant from unreadable policy storage.
  The former omits only affected tools/prompts from discovery while independently
  allowed entries remain; a direct call depending on that uncertainty is temporarily
  unavailable. A failed policy read fails the dependent listing/call; it must not
  masquerade as a successful empty listing. Include both cases and positive controls.
- [ ] On an approved isolated fault fixture only, simulate a policy read failure
  and delayed cleanup, restore it, and verify temporary refusal without guessed
  allows/destructive cuts. Delayed cleanup after a committed change retains that
  result and pending work; it does not by itself mean policy storage is unreadable.
  Do not corrupt shared staging, add production test hooks or suppress diagnostics.

Acceptance: all required matrix rows pass and the security owner accepts the
explicit cache, federation, distinct-mount and lock boundaries for this topology.
Unacceptable exposure or a required boundary that cannot be tested blocks closure;
no policy weakening or broad “not applicable” exception is allowed.

### S5 — Validate real UI, themes and accessibility

Owner: UI/accessibility reviewers. Consumes S2–S4 and the companion checklist.

- [ ] Exercise administrator and personal pages using the actual host session/CSP,
  deployed theme, light/dark modes, narrow viewport and 200% zoom. Record supported
  browser versions, keyboard-only behavior and a named screen-reader/browser pair.
- [ ] Follow H-UI in the companion checklist: navigation, focus, dialogs, live
  announcements, unknown/error states, saves/conflicts, reset/undo, client controls
  and read-only personal scopes. Check that translated labels fit and make sense.
- [ ] Reproduce switching Alice to Bob while browse/reload/save/undo responses are
  delayed, including failures and a detached save control. No old state, receipt
  or timeout may overwrite Bob's editor; requests remain bound to their owner.
- [ ] Trigger a stale revision and an interrupted response. Verify no automatic
  write replay or false success; reload establishes actual state. A committed
  change with pending cleanup must not be misreported as a rolled-back write.

Acceptance: no cross-user action, inaccessible mandatory control, misleading save
status, blocked asset or unhandled browser error. Manual evidence supplements the
609 synthetic browser cases; it does not replace them or imply an accessibility
certification beyond the tested combinations.

### S6 — Rehearse the operator's coordinated recovery

Owner: backup operator and security reviewer. Separate approved recovery window;
use the real backup tooling/database/storage topology selected at S0.

- [ ] Seed a live access/refresh pair, a pending code with its known PKCE verifier,
  a native app password and a restricted fixture account. Verify pre-backup validity
  without consuming the pending code. Enter maintenance/quiesce writes, take the
  coordinated backup, then revoke credentials through the approved administrative
  path. Record event order privately so the backup demonstrably predates revocation.
- [ ] Keep maintenance and public ingress closed while restoring matching
  app/database and required configuration/data; restart caches/workers. Do not roll
  files back alone or reopen old code unable to enforce required restrictions.
- [ ] Record issuance/expiry and the restored epoch/generation privately before
  the recovery cut. The authorization-code lifetime is 300 seconds in the pinned
  `TokenService`, so a full backup/restore may outlast it. Never extend expiry,
  alter rows or change the clock to obtain a pass. If a saved artifact has expired,
  record that result as expiry-only and obtain an unexpired same-user/client
  control after restoration but before the recovery cut, behind the independent
  ingress barrier. Fresh consent advances issuance generation: record that new
  generation and the unchanged pre-cut epoch, not an assertion that it is the old
  credential. After cutting, privately verify that both the saved and control
  credentials have an obsolete epoch or a generation at/below `revoked_below`,
  matching the production `CredentialGeneration::live` rule. Pair that state
  evidence with the unexpired control's protocol refusal; label the actual backup's
  expired-artifact result separately. If the state comparison or safe control is
  unavailable, credential-cut evidence remains blocked rather than treating expiry
  as revocation. Never alter the clock, row or credential lifetime for this check.
- [ ] Before reopening, use supported policy controls to invalidate restored OAuth
  credentials and explicitly disconnect fixtures. Review effective scopes/ACLs;
  separately revoke the restored native app password via native Security controls.
  Use the S0 administrative path; if maintenance must be lifted for these controls,
  first verify the independent ingress barrier admits only the recovery operator.
  Direct database edits are not a recovery API.
- [ ] Lift maintenance only behind that tested ingress barrier, enable the service
  and explicitly reconnect the fixture. Using the same reachable test path, prove
  fresh OAuth succeeds with the expected scopes while the restored old access and
  refresh tokens and pending code remain refused. Prove revocation with the still
  unexpired saved artifacts or the explicitly recorded pre-cut lineage controls.
  Check old/new app passwords on a native authenticated endpoint as well as MCP,
  so a personal disconnect cannot falsely stand in for native password revocation.
- [ ] Reject a false green caused by maintenance/closed-service responses, firewall
  rejection, expiry, wrong verifier/client or missing personal connection.
  Compare protocol-specific invalid-credential responses with fresh positive
  controls. Measure recovery and data loss against S0's RTO/RPO definitions, then
  close MCP and remove temporary test access before ending the exercise.

Acceptance: restored state cannot revive revoked access; fresh authorized access
works with required restrictions; backups are usable and agreed recovery objectives
are met. The prior SQLite rehearsal is context, not evidence for this operator's
backup tooling or another database/storage arrangement. Failure blocks approval.

### S7 — Human sign-off and acceptance report

Owner: maintainer, security/operations owners and named human reviewers.

- [ ] Complete H-DOC, H-SEM, H-UI and H-OPS in the companion checklist, including all
  96 per-page approvals and runtime language review. Retain pending notices until
  humans approve actual content; automated validation never supplies that approval.
- [ ] Reconcile all scenario IDs, defects, retests and approved limitations in the
  staging report. No missing result, unresolved security/compatibility blocker or
  blanket waiver may disappear into a green aggregate.
- [ ] Apply the candidate-change rules below before final approval. Record the
  installed final hash, all repeated scenarios and any evidence carried forward
  from identical content. A correction may reopen an earlier phase; do not approve
  the old candidate and silently substitute a later package.
- [ ] Record signatures/date, candidate digest, topology scope and one verdict:
  `ACCEPTED FOR THE RECORDED STAGING SCOPE`, `BLOCKED`, or `PARTIAL EVIDENCE`.
  Only the first plus all human gates closes this acceptance plan. Partial evidence
  is useful but never “all upstream acceptance complete”.
- [ ] Keep GitHub CI execution, release signing/publication and production rollout
  as separate unexecuted gates. Schedule no push, PR, release or deployment from
  this sign-off; each requires its own user authorization and exact candidate.

Acceptance: the signed report links every mandatory result to the final artifact,
all human approvals are current, and the remaining release actions are explicit.
An accepted staging candidate is not an authorization to deploy it.

### Candidate-change and defect gates

| Change after qualification | Required requalification before S7 closes |
| --- | --- |
| English development-only plan/report edits, excluded from package | Docs/provenance/tooling checks; no claim of changing the installed artifact. |
| Distributed documentation, translation or review-notice/metadata edits | Human approval of final text, docs/provenance/tooling and complete package checks; new archive hash, S2 installed-byte verification and affected offline/rendered-language checks. Record exact code/asset equivalence before carrying forward behavioral evidence. |
| Runtime catalog, browser or other application behavior change | Full canonical `composer --working-dir=mcp check`, package verification, affected runtime/native gates and affected S3–S6 scenarios; repeat UI/language approval for changed journeys. |
| Shared policy, schema, authentication or cross-capability behavior change | Full canonical check, strict PHP 8.2–8.5 qualification and all 14 native cells on the final candidate; repeat affected staging scenarios, including S6 when recovery semantics change. |

Use [testing](../testing.md), [packaging](../packaging.md) and the pinned closure
report for exact local qualification evidence. If impact cannot be bounded,
choose the broader gate rather than assume an unrelated change. Even a metadata-only
Composer root-reference change needs a documented file comparison and reviewer.

Security/privacy exposure, credential revival, data loss, failed native access
controls, wrong-user writes, broken supported flows and inaccessible mandatory
controls block acceptance. Other unresolved defects retain severity, owner, impact
and a specific maintainer disposition; acceptance cannot silently drop them.
A known limitation can be accepted only within the stated contract and topology,
not used to waive a failed mandatory scenario or redefine support without review.

## 7. Execution report structure

The future report must contain the S0 manifest/authorizations, phase start/end
records, per-scenario results, sanitized artifact references and hashes, defects
and retests, per-page human approvals, recovery measurements, accepted limitations,
final verdict and remaining release gates. Reviewer names and evidence references
must be real; do not fill them with fabricated sample approvals. Record blocked
inputs at their owning phase and continue only independent review work.
