# LinuxServer upgrade and recovery testing

The explicit LinuxServer runner exercises Nginx/PHP-FPM, PostgreSQL and S3 in a
private disposable fixture. It complements the Apache matrix and never operates
on an arbitrary or production Nextcloud instance. Ordinary `composer check`
executes only its runner boundary tests.

## Inputs and planning

Use the [development toolchain](setup.md). Planning requires Node and a complete
verified [source kit](source-delivery.md). Execution additionally needs Docker,
Python 3.12+, OpenSSL, Linux network/disk tools, the already-pulled pinned images,
retained companion-app archives, PHPUnit PHAR and the required CLI tokenizer APK.
The [runner guide](../../../mcp/tests/Integration/README.md#linuxserver-baseline-admission)
describes baseline inventory generation and input admission.

The executable profiles own the exact images, archives, source SHA and trusted
manifest: [upstream 1.2.0 origin](../../../mcp/tests/Integration/ci/linuxserver/profile.json)
and [upstream 1.2.1 origin](../../../mcp/tests/Integration/ci/linuxserver/profile-121.json).
Both bind a specific 2.0.0 kit, not the current checkout. Do not invent a matching
digest for a different kit. Review and renew the profile when selecting a new
candidate.

Prepare the private input directory with these exact names:

| Input | Name and authoritative pins |
| --- | --- |
| Baseline app | `mcp-<baseline.version>.tar.gz` and `baseline-inventory.json`, verified against the profile's `baseline` object |
| Companion apps | `<app.id>-<app.version>.tar.gz` for each entry in the profile's `apps` array; retain the reviewed archive bytes |
| Native tests for L3/L4 | `phpunit.phar` and `php85-tokenizer-8.5.12-r0.apk`; exact hashes are enforced by [L3 lifecycle](../../../mcp/tests/Integration/ci/linuxserver/l3-lifecycle.mjs) |
| Update-control probes | The `protection/` tree generated by the tracked recipe below |

The [input staging code](../../../mcp/tests/Integration/ci/linuxserver/inputs.mjs)
checks the archive bytes and inventories before fixture execution. Missing inputs
fail instead of being downloaded or replaced during a run.

Run from the repository root, replacing the absolute paths and digest with the
reviewed inputs for that profile:

```sh
kit=/absolute/path/to/verified-kit
kit_sha=TRUSTED_MANIFEST_SHA256
inputs=/absolute/path/to/verified-inputs
profile="$PWD/mcp/tests/Integration/ci/linuxserver/profile-121.json"
composer --working-dir=mcp test:integration:linuxserver -- --plan \
  --fixture-profile "$profile" --kit "$kit" --manifest-sha256 "$kit_sha"
composer --working-dir=mcp test:integration:linuxserver -- --check-baseline \
  --inputs "$inputs" --fixture-profile "$profile" \
  --kit "$kit" --manifest-sha256 "$kit_sha"
```

`--fixture-profile` is the unambiguous Composer-facing profile option. Planning
validates inputs without starting containers; it does not prove image availability,
native readiness or production suitability.

## Execution phases

| Phase | Purpose | Required evidence |
| --- | --- | --- |
| L1 | Bootstrap the pinned baseline | Native identity, storage and application checks |
| L2 | Seed synthetic state and capture B0 | Consistent baseline database, app/config/data and S3 checkpoint |
| L3 | Chain fresh L1/L2, upgrade the exact kit and capture B1 | Preserved state, installed-tree identity and post-upgrade checkpoint |
| L4 | Restore retained L3 checkpoints and test credential cuts | Complete candidate recovery, coordinated baseline rollback and rejection of incomplete imports |

Use `--phase L1`, `L2` or `L3` with the same kit/profile/input arguments. For
example:

```sh
composer --working-dir=mcp test:integration:linuxserver -- --phase L3 \
  --inputs "$inputs" --fixture-profile "$profile" \
  --kit "$kit" --manifest-sha256 "$kit_sha"
```

For L4, supply the absolute L3 evidence directory and the exact B0/B1 generation
and manifest hashes from its trusted result:

```sh
composer --working-dir=mcp test:integration:linuxserver -- --phase L4 \
  --inputs "$inputs" --fixture-profile "$profile" \
  --kit "$kit" --manifest-sha256 "$kit_sha" \
  --checkpoints "$l3_evidence" --b0-generation "$b0_generation" --b0-sha256 "$b0_sha" \
  --b1-generation "$b1_generation" --b1-sha256 "$b1_sha"
```

L4 verifies checkpoint bindings before restoration. It restores matching app,
database, configuration/data and S3 state with ingress closed, rejects restored
old credentials and tests explicit reconnection. App-password lifecycle remains
separate. A file-only rollback is not a supported recovery procedure.

L5 names the subsequent evidence review; `--phase L5` is rejected. Failed required
checks remain failures even when some recovery subcases pass. Do not infer success
from a retained checkpoint or from an individual probe's output.

## Update controls and operator-owned paths

The 1.2.1 profile adds update-policy probes after recovery. Prepare their pinned
catalog input with
`python3 mcp/tests/Integration/ci/linuxserver/protection-inputs.py "$inputs"`.
The separate `--check-mount` and `--check-operator-paths` modes use the same
profile, kit, input directory and both L3 checkpoint trust pairs as L4. They are
mutually exclusive.

A read-only `mcp/` bind does not protect the loaded code if the service account can
rename its parent or redirect `apps_paths`. `--check-mount` reproduces that bypass
and must report substitution with a nonzero exit. It is a negative control.

The operator-path trial separates serving and maintenance roles:

| Surface | Serving role | Maintenance role |
| --- | --- | --- |
| `/app`, including the document root | Read-only bind anchored at container root | Same read-only tree |
| `/config`, including app roots and Nextcloud/Nginx/PHP configuration | Read-only, with a separate writable log area | Restored volume opened for explicit maintenance |
| Business data, PostgreSQL and S3 | Writable as required | Same stores |
| HTTP ingress | Operator-controlled admission gate | Serving container removed; CLI-only maintenance |

The trial checks mutations and parent/configuration redirection as the serving
account, the actual class loaded by CLI and FPM, MCP admission, complete runtime
inventory, signed updates of another app and a subsequent container recreation.
Filesystem protection of the effective path and configuration is the boundary;
`appstoreenabled=false` alone does not create it.

Use `--host-startup-inputs /absolute/private/inputs` only with
`--check-operator-paths` for the fixed OCR startup-hook replay. Inputs are `hook.sh`
and signed APK repository views at
`{main,community}/x86_64/{APKINDEX.tar.gz,*.apk}`. The
[tracked package inventory](../../../mcp/tests/Integration/ci/linuxserver/alpine-ocr-packages.json)
and runner validate the fixed bytes before mounting a read-only private mirror.
This is a fixture contract, not a general hook executor or deployment procedure.

## Evidence and limits

Resources have generated run ownership, an internal network and no published
ports. Cleanup applies only to that run's resources. Keep checkpoints, raw logs,
keys and synthetic credentials outside Git; publish only reviewed sanitized
results. Record the runner revision, selected profile, kit/checkpoint hashes,
required-case results, exit status and cleanup outcome.

The fixtures do not certify a production backup system, every S3 implementation,
public HTTPS or a hosted assistant. Host image/startup changes need separate
qualification. Use [installation and recovery](../installation.md#upgrade-and-recovery)
for operator-facing guidance and [testing](testing.md) for the other verification layers.
