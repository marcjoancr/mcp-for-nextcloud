## Before authorizing the change

1. **Establish a recoverable production baseline.** Identify the active database
   and roles, applied MCP migrations, persistent app/config/local-data volumes,
   object store and any other writers. Verify ownership and access. Provide a
   dated backup reference binding the same quiescent generation of **all four**
   stores. Confirm payload integrity, role restoration, S3 metadata and who can
   perform recovery. Coolify's own pre-update backup setting covers a different
   scope.
2. **Measure a real restore.** Restore that production generation in an approved
   isolated destination, then verify the 1.2.1 app, DB, objects and client state.
   Record the worst observed forward time through the commit-or-rollback decision,
   the full restore **including revalidation**, and a contingency approved by
   the owner. Devbox synthetic timings do not supply those values.
3. **Reserve time.** From 08:00 Madrid subtract the measured restore/revalidation
   and contingency to obtain the mandatory rollback decision time. Subtract the
   forward time through that decision to obtain the latest start. Also fit the
   successful activation and final smoke tests before 08:00. While the inputs
   are unknown, keep the live installation serving and leave the start unscheduled.
4. **Approve the target topology.** Confirm effective Compose mounts, reachable
   source offer, operator identity, exclusion of automatic MCP replacements,
   maintenance-only signed updates, expected hook inputs, gate and rollback
   owner. Record a separate production GO after the conditions above are met.

## Cutover and rollback after a GO

- Close ingress and background writers, confirm admission is closed, capture and
  verify the final coordinated checkpoint, then remove the serving container.
- Stage the authenticated source/runtime through the isolated maintenance role.
  Verify one selected MCP root, all runtime hashes and source metadata. Run the
  rehearsed `occ upgrade` and check core/app versions and migration state before
  starting the protected service.
- With ingress still closed, confirm the sealed mounts, successful hook, OCR,
  CLI/FPM class identity, Nginx health, retained access rules, signed companion
  apps and source retrieval. Test controlled private admission and a normal
  user's MCP initialization. Resume writers and reopen only on acceptance.
- On a mismatched artifact, changed grants, unusable storage, failed readiness,
  or reaching the rollback decision time without acceptance, close admission
  and stop writers. Restore the **entire** matching checkpoint to the previous
  image/configuration. Verify DB, app, objects, access, credential handling and
  service health before reopening 1.2.1. Restoring app files alone would leave
  the upgraded database and objects in place.
